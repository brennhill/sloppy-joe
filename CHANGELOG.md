# Changelog

## Unreleased

## 2.0.1

- Python: wheel inspection now reports `<dist>.data/` files that install outside `site-packages` as blocking `metadata/python-startup-hook`s. pip and uv install `<dist>.data/data/<rest>` at `sys.prefix/<rest>`, so `<dist>.data/data/lib/python3.12/encodings/aliases.py` replaces the standard library of a base interpreter (system Python, Docker images) and runs at every start; `Lib/`, `DLLs/` and the stdlib zip on Windows are covered too. A module named after a standard-library module in the scripts directory (`<dist>.data/scripts/json.py`) is reported because console scripts import it instead of the standard library, as are files that replace the interpreter, `pyvenv.cfg`, `._pth` or an activation script (`<dist>.data/scripts/activate`, `bin/python3`). On Windows `<dist>.data/data/x.pth` and `sitecustomize` at the prefix are startup hooks, since `site` treats the prefix as a site directory. Ordinary scripts, headers and other data files are not reported. Wheel results cached by the older inspector are discarded.

## 2.0.0

Major release: behaviour changes that can newly block a scan, most of which close the red-team findings.

- Breaking: the Action is now tagged `v2`; `latest` resolves to the 2.x release.
- Breaking: Python environment markers no longer remove a package from the scan, and `--python-platform`, `--python-arch` and `--python-version` only choose which locked versions Poetry/uv resolve. A package with a different source per platform can now block with "resolves from multiple sources".
- Breaking: `--ci` no longer errors on legacy Python manifests beside Poetry/uv; they are scanned as their own projects.
- Breaking: pnpm lockfiles must be `lockfileVersion: '9.0'`; names matching only an `internal` prefix block unless the public registry has no package of that name; Gradle subprojects no longer inherit a root's top-level `dependencyLocking` block.

- New command: `sloppy-joe fix-lockfile [--dir D] [--type T] [--config C] [--write] [--json]`. It plans every lockfile problem `check` blocks on as `fixable`, `guided` (manual command and the reason automation is refused) or `human` (no safe fix), runs the fixable ones in a private 0700 scratch copy (argv only, environment built from nothing, scripts disabled by flag and environment, timeout, output cap, no stdin), and writes a candidate only with `--write` and only if it keeps every reachable locked version, integrity and source, parses with the scanner's own parser and passes a `check --full` rescan; the previous file is kept as `<name>.sloppy-joe.bak`. Fixable: npm, pnpm (including 6.x to 9.0), Bun (including `bun.lockb`), Yarn Berry, Cargo, Composer, uv, Poetry (only when every package is locked with a wheel), go.sum, shadow lockfiles. Guided: Yarn Classic, Pipfile.lock, hash-locked requirements, Bundler, Gradle, .NET. Integrity, source and provenance findings, pins that disagree with the lockfile and dependency rewrites are never auto-fixed. Spec: `docs/specs/fix-lockfile.md`.
- `fix-lockfile --write` is all or nothing: it refuses, naming the file, when a `<name>.sloppy-joe.bak` already exists (it never overwrites a backup), checks every target and backup path for symlinks before changing anything, and undoes its earlier steps if a later one fails (a `bun.lockb` conversion can no longer leave both lockfiles behind). A `TMPDIR` that resolves through a symlink to a directory inside the project is refused.
- `--base-ref` runs git with `LC_ALL=C`, so a localised git no longer turns a manifest that did not exist at the ref into a blocking error.
- Every blocking lockfile-format or staleness error now names the exact manual command and its minimum tool version and points at `sloppy-joe fix-lockfile`. The go.sum remedy is now `go mod download all` (a bare `go mod download` stopped recording content hashes in Go 1.17).

- Similarity: typosquats that drop one character from a known name (`expres`, `typescipt`, `date-fn`, `body-parse`) raise `similarity/missing-char`. The dependency is compared locally against the popular lists and the exact names in the config, so no insertion fan-out of registry queries is added; names under four characters and popular packages themselves are not matched.
- Config: a package that matches an `internal` prefix (`acme-*`) only keeps internal (OSV-only) treatment when the public registry confirms no package with that name is published; otherwise, or when the lookup fails, `resolution/internal-source-unproven` blocks and the package is scanned like any other. Exact `internal` names are unchanged.
- Cache: cache files are trusted only when they and their directory belong to the current user, are not group- or world-writable, and match an HMAC-SHA256 integrity record (`<file>.mac`, keyed by a per-user key in the config directory). An edited, planted or copied-in cache file is discarded with a warning and refetched.
- .NET: a `.sln` or `.slnx` that lists a project other than `.csproj`/`.fsproj`/`.vbproj` (solution folders excepted) now blocks, since restoring the solution restores it unscanned. Any other MSBuild project file (`.proj`, `.sqlproj`, ...) that declares `PackageReference`, `PackageDownload`, `GlobalPackageReference`, `PackageVersion` or a versioned SDK blocks too.
- Ruby/Maven: the new-package check (`metadata/new-package`) now runs. RubyGems' gem endpoint has no creation date, so the first publish date is read from the gem's version list; Maven Central's is the POM date of the first version `maven-metadata.xml` lists. A first publish date that cannot be read is a metadata lookup error (blocking), never treated as an old package.
- Cargo: `.cargo/config.toml` (and `.cargo/config`) above the scanned directory is now read, as Cargo does. Configs up to the git root are repo-visible and merged like those inside the scan root; configs above the repository (or above the scan root without a checkout) are host-local and block unless `allow_host_local_cargo_config` is set, exactly like `CARGO_HOME`.
- Gradle: `dependencyLocking { }` is parsed instead of matched by keyword. Only `lockAllConfigurations()` and the lock mode (`lockMode = LockMode.X`, `lockMode.set(...)`) are understood; `unlockAllConfigurations()`, `lockFile` (which pointed Gradle at a different lockfile than the one scanned), `ignoredDependencies`, `deactivateDependencyLocking()`, any other setting, a locking call outside the block and a block nested anywhere but `allprojects`/`subprojects`/`buildscript` now block. An enclosing build script now locks the project only through `allprojects { }` or `subprojects { }`, since its own top-level block configures the root project alone.
- Gradle: scanning a subproject (`--dir app`) now reads the build scripts of its enclosing projects up to the build root (the nearest `settings.gradle`). Their repositories are verified, the dependencies their `allprojects { }`/`subprojects { }` blocks declare are scanned, their buildscript classpath and plugins are included, and a dependency declared in any other cross-project block (`project(':app') { }`, `configure(...) { }`) blocks.
- Composer: a package listed in both `packages` and `packages-dev` of `composer.lock` no longer keeps only the dev entry. A direct dependency resolves to the production (`packages`) version, so a vulnerable production version can no longer hide behind a clean dev entry, and the full scan checks every locked version, each at its own version.
- OSV: package names are queried in the form the registry publishes, since OSV matches names exactly. Packagist names are lowercased, PyPI names PEP 503 normalized, and NuGet ids are queried with every spelling nuget.org reports for the package (its registration `catalogEntry.id`), so `newtonsoft.json` in a `.csproj` is matched against advisories filed for `Newtonsoft.Json`. A NuGet package whose published id cannot be read blocks, a registration entry whose id names another package blocks, and an unknown ecosystem in an OSV query is an error instead of being queried as npm. Cached OSV results are keyed by every spelling queried.
- Python: the `resolution/python-legacy-manifest` warning for `requirements*.txt`, `setup.py`, `setup.cfg`, a non-Poetry `pyproject.toml` or a Pipfile without `Pipfile.lock` now says that only the declared packages are checked and that the dependencies pip resolves for them at install time are not scanned.
- Python: `PYTHON_VERSION`, `SLOPPY_JOE_PYTHON_VERSION`, their `*_FULL_VERSION` variants and `--python-version` are trimmed and split into `python_version` (`X.Y`) and `python_full_version`, so `PYTHON_VERSION=3.12.1` (as Docker images set it) is Python 3.12 and a configured version no longer pairs with the host interpreter's full version. An unreadable setting leaves the version unknown (markers on it count as true) instead of falling back to the host.
- Python: requirements comments follow pip's `(^|\s+)#` rule with Python whitespace (U+001F and NBSP before `#` start a comment, and a `#` inside quotes still does), so `pkg==1.0<U+001F>#; sys_platform == "win32"` is read as the unconditional `pkg==1.0` pip installs. `setup.cfg` continuation lines follow configparser: any line indented deeper than its option in Python whitespace (NBSP included) continues the value, so an NBSP-indented `install_requires` entry is no longer read as a separate, ignored option.
- Python: `requirements*.txt` (including `requirements/*.txt`), `Pipfile`, `setup.py` and `setup.cfg` beside a Poetry or uv `pyproject.toml` are scanned as their own projects instead of being reported as ignored (a warning outside `--ci` let their packages install unchecked).
- Python: the environment-marker evaluator follows pip, uv and Poetry. Version markers compare by PEP 440 (`python_version == "3.*"` matches 3.12, prereleases such as `3.13.0rc1` are detected with `platform.python_version()` and compared as versions), `platform_machine` uses the name Python reports on each OS (`arm64` on macOS, `aarch64` on Linux, `AMD64`/`ARM64` on Windows), `extra` names compare normalized, `~=`/`===` and the dotted `os.name`/`sys.platform` spellings parse. A comparison the tools disagree on (`< "3.*"`, `< 3.13` for a 3.13 prerelease, an unknown Python version or OS/arch pair) is undecided and counts as true instead of excluding the dependency. Markers nested deeper than 32 parentheses or longer than 4096 tokens block instead of overflowing the stack.
- Python: environment markers no longer hide packages. A dependency whose marker is false on the scanning host (or for `--python-platform`/`--python-arch`/`--python-version`) still gets source policy (untrusted or undeclared indexes, unauthorized sources, lock hash proofs) and existence, metadata and vulnerability checks; for Poetry and uv the target only decides which locked version it resolves, and locked packages other environments install are checked like transitive dependencies. Lockfile-less `requirements*.txt` and non-Poetry `pyproject.toml` scan every dependency whatever its marker.
- Python (uv): lock edges gated on uv's encoded `[tool.uv] conflicts` markers (`extra == 'extra-4-proj-b'`, `group-<N>-...`, `project-<N>-...`) are kept in the coverage graph. They name the project's extra or group, not the requesting package's, so they were always false and a package reached only through them (for example `rfc3986` from an untrusted index under `--python-extras b`) escaped source policy and the scan.
- Python (uv): every manifest dependency in scope for some environment must be recorded in `uv.lock` (root metadata entry with the same specifier and a locked version that satisfies it), as `uv lock --check` requires. A dependency whose marker is false for the scan target (`zzz-not-a-real-pkg==1.0.0; sys_platform == 'win32'` scanned on Linux) and that the lock does not record used to pass; it now blocks like an unmarked one. Poetry already blocked this.
- Python (Poetry/uv): a direct dependency whose marker is false for the scan target is checked as a direct dependency (canonical policy, similarity, existence, metadata, advisories) at its locked version, in every scan mode. It used to be demoted to the transitive list, so `requestz==2.31.0; sys_platform == 'win32'` lost its similarity finding in `--full`/`--ci` and got no checks at all in fast mode, bypassing `canonical` policy. The target still chooses which versions resolve.
- Python: a fully hash-locked `requirements.txt` no longer hides `requirements-dev.txt`, `setup.py` or `setup.cfg` beside it; each is scanned as its own project.
- Python: wheel startup-hook inspection can no longer be bypassed by how a wheel is written. Member names are resolved as pip and uv install them (`./x.pth`, `pkg/../x.pth`, doubled slashes, backslashes, Windows trailing dots, `<dist>.data/data/lib/pythonX.Y/site-packages/x.pth`); `sitecustomize`/`usercustomize` count in any importable form, including a `sitecustomize/` package; a `.pth` with only directory lines and a Python 3.15 `*.start` file are hooks. `.pth` lines are split like Python's `str.splitlines` after a BOM (lone CR, FF, NEL, U+2028, ...), decoded as UTF-8 and Latin-1, and stripped as Python 3.15 does. A wheel whose zip installers could read differently (zip64, a central directory not ending at the end record, a second end record, trailing data, local headers naming other files, NUL in a name, encryption) or with an ambiguous member name (absolute, escaping, `:`) blocks as `metadata/wheel-unverified`. Wheel results cached by the older inspector are discarded.
- Guardrails: a second, `syn`-based check of layer direction (`tests/architecture/syn_graph.rs`) runs beside the text scanner; `syn` and `proc-macro2` are dev-dependencies only.
- Ruby: a `Gemfile.lock` line indented with a tab or another non-space character now blocks. Bundler reads only space-indented entries, so such a line was silently dropped from the scan (a tab-indented transitive gem was never checked). Found by the new metamorphic test, which mutates each fixture lockfile (CRLF, BOM, NUL, lone CR, U+2028, U+0085, VT, FF, tab indentation) and requires the scanner to read the same packages or refuse the file.
- Gradle: a `gradle.lockfile` line that is not `group:artifact:version=configurations`, `empty=configurations` or a comment now blocks, naming the line, instead of being skipped (a skipped line could hide a pinned dependency from the scan).
- Bun: `bun.lock` package entries are held to a closed shape; a tuple with more than four elements blocks, and a metadata key Bun does not write blocks, naming the entry and the key (`config_key_allow` with file `bun.lock` permits one more exact metadata key).
- Yarn: `yarn.lock` entries (classic and Berry) are held to a closed key schema; a property or section Yarn does not write blocks, naming the entry and the key (`config_key_allow` with file `yarn.lock` permits one more exact key).
- pnpm: `pnpm-lock.yaml` `packages` and `snapshots` entries are held to a closed key schema; a key pnpm does not write blocks, naming the entry and the key (`config_key_allow` with file `pnpm-lock.yaml` permits one more exact key).
- Python: `uv.lock` and `poetry.lock` `[[package]]` entries and `Pipfile.lock` `default`/`develop` entries are held to closed key schemas; a key the tool does not write blocks, naming the entry and the key (`config_key_allow` with file `uv.lock`, `poetry.lock` or `Pipfile.lock` permits one more exact key).
- Cargo: `Cargo.lock` `[[package]]` entries are held to a closed key schema; a key Cargo does not write blocks, naming the entry and the key (`config_key_allow` with file `Cargo.lock` permits one more exact key).
- Composer: `composer.lock` package entries are held to a closed key schema; a key Composer's lock dumper does not write blocks, naming the entry and the key (`config_key_allow` with file `composer.lock` permits one more exact key; `transport-options` is never allowed).
- npm: lockfile entries in `package-lock.json`/`npm-shrinkwrap.json` are held to a closed key schema. An entry key that npm's arborist does not write now blocks, naming the entry and the key; a `config_key_allow` entry with file `package-lock.json` permits one more exact key and is reported as a `config/key-allowed` warning. Spec: `docs/specs/verification-and-schemas.md`.
- npm/yarn: a lockfile `resolved` value without a literal `https://` (for example `registry.npmjs.org/x/-/x-1.0.0.tgz`, which npm installs as a local file) is no longer treated as a registry tarball and blocks; a pnpm importer whose lockfile target is a different package than the manifest declares (`is-number` resolving to `ms@2.1.3`) blocks in every mode.
- Gradle/Maven properties: `\r\n` is one line terminator when parsing Java Properties, so a backslash continuation across CRLF can no longer hide a wrapper `distributionUrl` or a `-javaagent` in `org.gradle.jvmargs`. .NET: `RestoreConfigFile`, `RestorePackagesPath`, `RestoreRootConfigDirectory`, and `nuget.config` `globalPackagesFolder`/`repositoryPath` block. Python: `tox.toml`, `setup.cfg` with tox sections and `[tool.tox]` in pyproject are flagged like `tox.ini`.
- Cargo: rustflags/rustdocflags tokens starting with `@` (argfiles), `-l`/`-L` native-link flags and `llvm-args` block; a repo `.cargo/config.toml` `[env]` now allows only `RUST_BACKTRACE`, `RUST_LIB_BACKTRACE` and `RUST_LOG`; a workspace member outside the scan root blocks instead of being skipped.
- Ruby: every version of a gem in `Gemfile.lock` is scanned (a platform variant such as `nokogiri 1.13.0-x86_64-linux` no longer hides behind a later plain version), platform suffixes are stripped for registry, OSV and version-age lookups, and a direct gem locked at different versions is `resolution/ambiguous`. Guardrails: a file declared by a plain `mod` is production even if a `#[cfg(test)] #[path]` module also includes it, and a cfg(test) `#[path]` onto a shared file is flagged.
- npm: a non-boolean `link`, `inBundle` or `bundled` value in `package-lock.json` blocks (npm reads any truthy value as set; sloppy-joe only modeled `true`, so a string `link` was checked as a registry package while npm symlinked a repo directory). Maven: a parent `<version>` written as a property (`${revision}`) is now interpolated from the child's properties and its parent loaded, and blocks if the property is undefined, instead of silently ending the parent chain; a local parent POM that exists but is unreadable, has no `<project>`, or writes its coordinates with CDATA or XML entities now blocks instead of falling back to the same-named POM on Maven Central. Discovery: a file that is a manifest only under another capitalization (`Package.json`, `CARGO.TOML`) blocks, since case-insensitive filesystems read it.
- Maven/Gradle: a dependency version of `LATEST`, `RELEASE` or anything containing `SNAPSHOT` (also through `${property}`) is no longer treated as an exact pin; it now raises `resolution/no-exact-version` like a version range, instead of passing the fast scan with no findings.
- Red-team round 5 (guardrails): the layer check now sees calls through the crate root's re-exports and `use crate::*` globs, and test-only status comes from `#[cfg(test)] mod` declarations instead of `*_tests.rs` file names; aliasing `super`/`crate`/`ecosystems`, `macro_rules!` in orchestration and plugin code, `.parse::<Ecosystem>()` and `to_string() == "..."` are flagged. The manifest tree walk moved to `ecosystems::tree`.
- Cargo: `.cargo/config.toml` `include`, `build.rustc`/`rustdoc`, `target.*.linker`/`runner`, rustflags that set a linker, link args, codegen backend or `-Z` options, and `[env]` entries that redirect Cargo or rustc programs now block. `[workspace] members`/`exclude` are expanded and members inside ignored directories are scanned. Go: with `go` below 1.17 or no `go` line, modules in go.sum or `vendor/modules.txt` that go.mod does not list block; vendored builds get a `resolution/vendored-source-unverified` warning. .NET: `Directory.Build.rsp`, `Directory.Solution.props` and `.targets` block. Gradle: only `LENIENT` counts as lenient locking, and a `buildSrc` without a build script blocks.
- JavaScript: every `.pnpmfile.*` variant blocks, the hidden workspace-member search fails closed past 16 levels, an array or otherwise non-object `dependencies` section blocks, a bun.lock registry location outside `https://registry.npmjs.org/` blocks in every mode, and a `packageManager` version containing a URL blocks.
- Python: the requirements `coding:` line is read with pip's rule, trailing spaces after a continuation backslash end the continuation like pip, `-c` constraint files are no longer pruned, `uv.lock` artifact URLs must be on the index's own host, `uv.toml` index redirects are checked for every Python project, PDM `pdm.toml` indexes and sources, and a `hatch.toml` with environment dependencies block. In `--ci`, Poetry locks without hashes are strict errors, and legacy manifests, `environment.yml` and `tox.ini` deps beside Poetry/uv are errors (warnings otherwise).
- Ruby: a `.gemspec` that uses `send`, `public_send`, `__send__`, `method`, `define_method`, `instance_exec`, `class_exec`, `module_exec`, `const_get` or `binding` now blocks, since `s.public_send("add_" + "dependency", ...)` hid a dependency from the literal `add_dependency` scan.
- Python: the `poetry.lock` content-hash now matches what Poetry 2.x writes. Poetry hashes a missing legacy key (`source`, `extras`, `dev-dependencies`) as JSON `null` when `[project]` and `[dependency-groups]` carry no dependencies, treats an empty `[dependency-groups]` table as absent, and writes non-ASCII text as `\uXXXX` escapes; sloppy-joe omitted the nulls and so reported every fresh lock from a legacy `[tool.poetry]` project as "content-hash is stale". Verified against Poetry 2.4.1 for legacy and PEP 621 projects.
- Config parsing now models the tools' own line and separator rules instead of Rust's `lines()`: a lone `\r` (and `\f`, `\v`, U+2028 and the other Python line breaks) in `requirements.txt`, `setup.cfg`, `.npmrc` blocks, since pip, configparser and npm read text after it that the scan did not. Gradle and Maven wrapper properties are parsed as Java Properties (ISO-8859-1, `=`/`:`/whitespace separators, escapes, continuations) and unreadable ones fail closed. `.mvn/maven.config` options are matched by prefix (`-sfile`, abbreviated `--sett`), and `-f`, `-Dmaven.repo.local`, `-Dmaven.ext.class.path` block; `.mvn/jvm.config` also blocks `-agentlib`, `-Xbootclasspath` and class-loader overrides. Gradle `gradle.properties` with agent `org.gradle.jvmargs` or `org.gradle.java.home` blocks. A `Gemfile.lock` GEM `remote:` other than rubygems.org blocks.
- Gradle: `gradle.lockfile` is only trusted when the build turns dependency locking on (`dependencyLocking { lockAllConfigurations() }` in the build script or an enclosing one); without it Gradle ignores the lockfile, and `LockMode.LENIENT` lets unlisted dependencies resolve, so both block. Enclosing `settings.gradle` files are now found without a `.git` directory (Docker contexts, tarballs), and a `gradle-wrapper.properties` `distributionUrl` outside `services.gradle.org`/`downloads.gradle.org` blocks. Maven: `.mvn/settings.xml`, `.mvn/toolchains.xml`, `-s`/`--settings`/`-t`/`--toolchains` options in `.mvn/maven.config`, `-javaagent` in `.mvn/jvm.config`, and a `.mvn/wrapper/maven-wrapper.properties` URL outside Maven Central now block.
- Python (uv): `index-url`, `extra-index-url`, `find-links`, `no-index`, `index-strategy` and `default-index` under `[tool.uv]`, `[tool.uv.pip]` or a `uv.toml` in the project directory or a parent now block; plain `uv sync` re-resolves with them, so the lockfile no longer vouches for the install. The supported `[[tool.uv.index]]` declarations are unchanged.
- JavaScript: a top-level `patchedDependencies` (bun) now blocks like pnpm's patches, since the patch changes installed code the scan never saw.
- .NET: PackageReference and other item names are matched case-insensitively (`<packagereference>` used to be skipped), `<project>.csproj.user` files, `NuGetLockFilePath` and `RestorePackagesWithLockFile` other than `true` now block, since each leaves the committed `packages.lock.json` unused or a decoy.
- Architecture guardrails: whitespace around `::` no longer hides a path or an `Ecosystem::` variant, `super::<plugin>` is flagged at any module depth and in registry `use` statements, and comparing `as_str()` or `project_type` with a string literal in orchestration code is flagged.
- PHP: the full and CI scans now check each `composer.lock` package's `source` and `dist` locations and references against Packagist's p2 metadata for that name and version; a lock pointing a Packagist name at another repository on a trusted host (for example `github.com/attacker/log`), a version Packagist does not list, or an unreachable lookup now blocks. Root `scripts` keyed by any `pre-*`/`post-*` event or `init`/`command` (Composer runs them for plugin and command events during install) block, as does an `allow-plugins` pattern containing `*` such as `*/*`.
- .NET: a `<ProjectReference>` whose target does not exist or lies outside the scan root now blocks (it builds code no scan covers), and a `.csproj` beside an `.fsproj`/`.vbproj` in one directory is ambiguous because they share a single `packages.lock.json`. Gradle: `build.gradle` beside `build.gradle.kts` in one directory now blocks instead of scanning both as separate projects.
- Maven: a `.mvn/extensions.xml` in the project or any ancestor up to the repository root now blocks, since core extensions are loaded into Maven itself and run unscanned. Composer: `scripts` bound to install-time events (`post-install-cmd`, `post-autoload-dump`, package-level events and the like) and a blanket `config.allow-plugins` (`true` or `{"*": true}`) now block; named plugin approvals and non-install scripts such as `test` still pass.
- npm: a registry route set in the repository's `.npmrc` (default or scoped) that the out-of-repo config does not allowlist now blocks in every scan mode, as it already did in `--ci` and as yarn's `npmRegistryServer` always did. It used to be a warning in fast and full scans. Allowlisted routes still report the packages as unvetted.
- Cargo: a registry crate in `Cargo.lock` without a checksum now blocks (Cargo would trust whatever the index serves for it); lockfile v1 `[metadata]` checksums count. A repository's `.cargo/config.toml` that sets `http.proxy`, `http.cainfo`, `http.ssl-version`, `http.check-revoke`, `net.git-fetch-with-cli`, `build.rustc-wrapper`, `build.rustc-workspace-wrapper`, `registry.credential-provider` or `credential-alias` now blocks, since those redirect fetches or run programs the scan cannot verify.
- Go: a `vendor/modules.txt` no longer switches off the go.sum check by merely existing. While vendoring is in effect (go 1.14 or later), the listing must contain every required module version (`# <module> <version>`) or the scan blocks; before go 1.14, or without a listing, go.sum is enforced. go.sum must also carry the content hash (the entry without `/go.mod`) for every direct requirement, not just the `/go.mod` hash; `// indirect` requirements keep needing only the `/go.mod` hash.
- JavaScript: a `package.json5`, or a `package.yaml` that declares npm-style `dependencies`/`devDependencies` as a mapping, now blocks discovery instead of being skipped, so a repo no longer reports "0 packages, no issues" while a project's dependencies go unread. Haskell hpack `package.yaml` files (a list of dependencies) are still ignored; `ignore_dirs` excludes a directory outright.
- Scan: a lockfile that cannot be read for internal packages now blocks instead of scanning them with no resolved versions (which skipped their advisory checks).
- Scan: when project discovery finds nothing to scan but the legacy manifest parser reads a manifest, the scan now blocks with a discovery/parser mismatch error instead of reporting a clean zero-package scan.
- Build: update `tokio` to 1.53.3 (RUSTSEC-2026-0386, `AsyncFd` I/O-safety, affected 1.49.0), and allowlist the `sha1`, `flate2`, `tar` and `semver` crates in the repository's own self-check config so the CI self-check does not flag them as typosquats.
- Cargo: trust `Cargo.lock` for a ranged crates.io requirement (`serde = "1.0"`) when exactly one locked version satisfies it, using the `semver` crate (pinned `=1.0.28`) for Cargo's requirement rules. A lock that contradicts the requirement is `resolution/lockfile-out-of-sync`, several satisfying versions stay `resolution/ambiguous`, and an invalid requirement keeps `resolution/no-trusted-lockfile-sync`. This amends `docs/specs/cargo-provenance-hardening.md`; real projects such as `bat` and `fd` now scan cleanly. Other ecosystems keep the strict rule.
- Maven: derive versions the way Maven's effective model does. `${property}` references, `<dependencyManagement>` and `<pluginManagement>` entries, imported BOMs, and the `<parent>` chain (local reactor parents, otherwise POMs fetched from Maven Central) now supply versions, so Apache-style projects that manage plugin versions in a parent no longer block with `resolution/no-exact-version`. A parent or BOM that cannot be fetched fails the scan; a version that cannot be derived stays unresolved.

## 1.2.0

### Security and correctness

- Close dependency parsing and source-policy bypasses across Python, JavaScript, Ruby, Go, JVM, Cargo, and .NET projects.
- Preserve trusted policy boundaries when scanning subdirectories or relative paths.
- Keep metadata and vulnerability checks active for transitive dependencies and respect cache selection and bypass options.
- Reject future-dated security caches, preserve cache expiry on reuse, and record successful full scans only after passing checks.
- Enforce version-age policy when publication dates are missing or invalid, and account for timezone offsets.
- Bound package-name lengths before typo mutation generation.
- Avoid reporting Cargo hyphen/underscore spellings of the same crate as typosquats.
- Discard invalid generated package names before similarity queries instead of misreporting them as registry outages.
- Accept legacy registry UTC publication timestamps while preserving timezone-aware age checks.
- Include legacy Python build and test dependencies.
- Recognize packaged uv project roots and uv lockfiles without redundant tool metadata.
- Verify supported uv version ranges against exact locked selections instead of requiring redundant manifest pins, using PEP 440 parsing for prerelease, postrelease, and local versions.
- Follow OSV advisory pagination and reject malformed or incomplete query responses.
- Separate maintenance-only unmaintained notices from vulnerability records; retain blocking unsoundness advisories.
- Update affected direct and transitive dependencies to patched versions before release.
- Refresh README coverage against primary-source supply-chain incident reports and document heuristic limits.

### Compatibility notes

- Inputs whose dependency graph or source policy cannot be verified report an unsupported scan (exit 2).
- Legacy setup.py scanning accepts a restricted literal grammar. Executable setup logic, computed arguments, and custom source encodings are unsupported.
- Package names are limited to 214 bytes for npm and 1,024 bytes for other ecosystems.
